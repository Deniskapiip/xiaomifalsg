Проверены ошибки конфигурации без вывода секретов, атомарное обновление .env и конфликт параллельного редактирования, скрытый ввод без перехода к открытому вводу, необязательные менеджеры, временные роли, занятый порт и блокировка второго launcher. Проверки оркестрации подтверждают порядок: резервная копия → подключённый туннель → обновление URL → готовый backend. При ошибках запуска завершаются только собственные дочерние процессы.

Проверены сохранение последних 14 копий, целостность опубликованного файла, WAL с сохранёнными изменениями, исключение незавершённых транзакций, ограничение времени ожидания и удаление незавершённой копии. Чужие файлы и исходная база не удаляются ротацией.

Новые локальные DEV-заказы не создают сообщения клиенту и администраторам. После включения настоящего бота их маркер сохраняется, смена статуса также не отправляет сообщения. Если для помеченного заказа уже есть задание, worker пропускает его без вызова Telegram. Исторические немаркированные заказы не переклассифицируются.

## Проверки реальных процессов и HTTP

На отдельной мигрированной и заполненной демо-данными SQLite базе launcher трижды запускал настоящий FastAPI: для owner, manager и client. Проверены готовность health API, выдача собранного интерфейса, DEV-вход с соответствующей ролью, создание локального заказа, смена статуса менеджером и чтение заказа клиентом. В конфигурации присутствуют «В пути до получателя» и «Доставлен».

Для каждого запуска SIGINT завершал launcher и его backend; порт освобождался, повторная проверка и следующий запуск проходили. Исходный .env оставался побайтно неизменным. Три копии, созданные перед этими запусками, прошли PRAGMA quick_check. Telegram-бот и публичный туннель в этом сценарии не включались.

Дополнительно самостоятельная команда backup.py прочитала DATABASE_URL из .env при запуске из другой рабочей папки. Проверены имя SQLite-файла с кириллицей, пробелом, # и %, сохранённые изменения WAL и работа без настроек токена бота или JWT. URL с пробелами и # в .env заключён в кавычки.

Настоящие Vite и backend с отдельной SQLite базой проверены на портах 5173 и 8000: локальный вход через /api proxy вернул HTTP 200 и роль client. Каждый из заголовков x-forwarded-for, Forwarded и cf-connecting-ip блокировал DEV-вход с HTTP 403 DEV_LOCAL_ONLY. Оба процесса после проверки остановлены.

## Туннель и пределы проверки

Официальный Linux cloudflared 2026.10.0, собранный 05.10.2026, принял точные параметры launcher, включая отдельный пустой config, no-autoupdate и protocol http2. Процесс начал создание Quick Tunnel, но доступ к api.trycloudflare.com оказался недоступен из сети этой среды. Настоящий адрес не был получен, соединение с Cloudflare не зарегистрировано, публичный HTTPS-запрос не проверен. Тестовый HTTP-сервис и cloudflared остановлены.

Настоящий Windows, Telegram на Android/iOS, ввод реального токена и доставка настоящих сообщений здесь не проверялись. Ветви Windows process group и CTRL_BREAK_EVENT проверены с подменёнными процессами. Для фактической проверки используйте [STAGE-4-WINDOWS.md](STAGE-4-WINDOWS.md) и [ACCEPTANCE-TELEGRAM.md](ACCEPTANCE-TELEGRAM.md); неотмеченные пункты чек-листа остаются непроверенными.

Quick Tunnel предназначен для разработки; адрес меняется при новом запуске. Для постоянного размещения предусмотрен следующий этап проекта. Официальные сведения: [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/), [Telegram Mini Apps](https://core.telegram.org/bots/webapps), [ngrok для Windows](https://ngrok.com/download/windows).
