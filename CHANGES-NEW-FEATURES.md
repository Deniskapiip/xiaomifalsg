# Обновление Taoji Cargo: что добавлено и что менять при деплое

Документ описывает только изменения этой версии. Дизайн не менялся: все CSS-файлы,
палитра, шрифты, отступы, анимации и сетка остались прежними, поэтому `frontend/src/styles/*.css`
не тронуты, а размер собранного CSS совпадает с прежним (`61,76 kB`).

## 1. Telegram WebApp SDK

| Возможность | Реализация |
|---|---|
| Лёгкий haptic на каждое нажатие | `frontend/src/lib/telegram.ts` — `haptic('tap')` → `impactOccurred('light')`; один делегированный слушатель в `frontend/src/lib/telegram-ui.ts`, подключён в `main.tsx`. Отдельные `selection`/`success`/`error` остались в компонентах |
| `ready()` + `expand()` при старте | уже были в `initializeTelegram()`; добавлена безопасная проверка возможностей клиента |
| Нативные окна вместо `alert`/`confirm` | `showAlert`, `showConfirm`, `showPopup` в `telegram.ts`; используются для шаринга расчёта, удаления трек-номера и подсказок |
| Иконка на главный экран | `addToHomeScreen()`, `canAddToHomeScreen()`, `homeScreenStatus()`; блок на главной в `pages/Home.tsx` появляется только в Telegram 8.0+ и скрывается, если иконка уже добавлена |
| Автосохранение черновика | уже было в `store/wizard.ts` через CloudStorage + localStorage; теперь в черновик входят и выбранные доп. услуги, старые черновики читаются с значениями по умолчанию |

## 2. Парсер ссылок и калькулятор

- `frontend/src/lib/platforms.ts` (новый) — единое определение площадки по домену
  (`dw4.co`, `dewu.com`, `poizon.com` → Poizon / Dewu; `tb.cn`, `taobao.com` → Taobao;
  `tmall.com` → Tmall; `1688.com` → 1688; `goofish.com`, `xianyu.com`, `2.taobao.com` → Xianyu / Goofish)
  и по китайскому названию магазина (`闲鱼` → Xianyu, `得物` → Poizon и т.д.).
- `frontend/src/lib/product-share.ts` — `parseShareText(text)` вырезает ссылку из текста
  «Поделиться», понимает URL без схемы (`m.tb.cn/h.abc`), отбрасывает хвостовую пунктуацию,
  не путает домены-двойники и возвращает площадку с учётом иероглифов.
- `backend/app/platforms.py` не менялся; сервер по-прежнему определяет площадку по URL и
  сохраняет её в заказе, а бот и админка показывают русское название.
- Калькулятор (`pages/OrderWizard.tsx`, шаг «Вес»): блок «Доп. услуги» из трёх переключателей
  на существующих классах `tariff-grid` / `tariff-card is-selected`:
  страховка (% от стоимости товара), обрешётка/упаковка, фотоотчёт на складе.
  Суммы считает сервер, клиент повторяет формулу (`lib/pricing.ts`) для живого превью.
- Итоговый экран: в разбивке появились строки услуг и «Сумма доп. услуг»; главная сумма —
  `total_with_extras_rub` (товар + комиссия + услуги), `total_rub` не изменился.
- Кнопка «Поделиться расчётом»: `lib/calc-share.ts` формирует текстовое резюме,
  копирует в буфер (`copyText`), при успехе — haptic + нативное окно, при ошибке буфера —
  открывает чат менеджера с готовым текстом.

## 3. Трекинг и заявки в бота

- Заказ из Mini App по-прежнему уходит на `POST /api/orders`; бот сразу отправляет клиенту
  подтверждение, администраторам — карточку нового заказа. В карточку добавлены:
  площадка по-русски, выбранные доп. услуги и их сумма, трек-номер (если уже есть),
  ссылка, вес, `@username` и Telegram ID клиента.
- Админка: карточка заказа → блок «Трек-номер» (сохранить/удалить, уведомление клиента,
  событие `tracking` в истории). API: `POST /api/admin/orders/{id}/tracking`.
- Клиент: блок «Статус по трек-номеру» на экране «Мои заказы» — поиск по трек-номеру или
  номеру заказа (`GET /api/track?number=...`), карточка с текущим статусом, прогрессом
  (`Timeline`), весом и суммой; 404 показывается понятным сообщением.
- Бот: `/track <номер>` — статус, площадка, время обновления и трек-номер; без аргумента —
  подсказка. Команда добавлена в меню бота (`COMMANDS`).
- Уведомление клиенту о новом трек-номере: `CLIENT_TEXTS["tracking"]` + задание в очереди
  уведомлений; отключается флагом `notify`.

## 4. Backend и база

- Миграция `backend/alembic/versions/0002_order_options_tracking.py`:
  `insurance_enabled`, `packing_enabled`, `photo_report_enabled`,
  `insurance_rub`, `packing_rub`, `photo_report_rub`, `extras_total_rub`,
  `total_with_extras_rub`, `track_number` + индекс `ix_orders_track_number`. Есть downgrade.
- Цена тарифа задаётся в рублях или юанях (`price_currency`): юани пересчитываются по курсу
  на момент оформления, в заказ сохраняется исходное значение и RUB-снимок.
- Страховка доступна только на тарифах с флажком `insurance_available` (например, «Китай - Благовещенск»),
  процент — `INSURANCE_PERCENT` (по умолчанию 10). Обрешётка — `PACKING_FEE_RUB` за коробку (299),
  количество коробок указывает клиент. Фотоотчёт — `PHOTO_REPORT_FEE_RUB` (150).
  Все значения отдаются в `/api/config`, чтобы клиент и сервер считали одинаково.
- `POST /api/calc` принимает флаги услуг и возвращает полную разбивку.
  `POST /api/orders` сохраняет снимок сумм и услуг в заказе.
- Все деньги по-прежнему передаются строками; секретов в коде нет; новых зависимостей нет.

## 4.1 Мультизаказ, площадки, отзывы, причина отмены (вторая итерация)

- **Мультизаказ:** до 20 позиций в одном заказе. У каждой — своя ссылка, название, цена в ¥, количество
  и комментарий. Новая таблица `order_items` (миграция `0004`), в заказе сохранён снимок позиций;
  итог, комиссия и услуги считаются по сумме всех позиций. Старые заказы и старые клиенты API
  (одна ссылка) поддерживаются: при миграции каждый заказ получает одну позицию.
- **Мастер:** шаг «Товары» с карточками позиций, кнопкой «Добавить ссылку», удалением, подсветкой
  невалидной ссылки, прокруткой к первой ошибке и блокировкой «Далее». Автозаполнение товара
  работает для активной позиции; `/calc` получает суммарную цену, расчёт показывается по позициям.
- **Площадки и значки:** добавлен Pinduoduo; короткие `m.tb.cn` определяются как Xianyu/Goofish
  (случай `e.tb.cn`/`tb.cn` — Taobao), китайский текст по-прежнему уточняет площадку.
  Цветные брендовые значки (`PlatformMark`) показаны у каждой ссылки, в карточках заказов,
  в трекинге и админке; в токены добавлены брендовые цвета площадок.
- **Отзывы:** `REVIEW_USERNAME` (по умолчанию `taojiotziv`) в `/api/config.contacts.review`.
  После статуса «Доставлен» кнопка «Оставить отзыв» есть на главной, в завершённых заказах
  и в карточке заказа.
- **Причина отмены:** в админском диалоге отмены — поле «Что случилось?»; причина сохраняется
  в `payload.cancel_reason`, показывается в истории и добавляется в уведомление клиенту.
- **Бот:** админская карточка перечисляет все позиции (название, цена × количество, ссылка, площадка),
  клиенту при заказе из нескольких позиций пишется их число.

## 4.2 Трекинг посылок Добропоста

- Новый экран **«Трекинг посылки»** (из главной и из блока «Мои заказы»): клиент вводит трек-номер,
  тот сохраняется и проверяется автоматически **раз в 6 часов** (`TRACKING_REFRESH_HOURS`),
  на экране видны статус, время последней и следующей проверки.
- Трек-номер, отправленный боту `/track <номер>`, автоматически добавляется в отслеживание
  (если это не номер нашего заказа `TC-…`), бот сразу показывает текущий статус и кнопку в приложение.
- Ручное обновление — не чаще раза в 15 минут (иначе 429 `TRACKING_COOLDOWN`), удаление трека — из карточки.
- Таблица `tracking_links` + миграция `0005`; фоновая задача `TrackingWorker` в том же процессе,
  при смене статуса клиенту приходит уведомление в бота.
- Источник статуса — официальный трекинг-API `api.dobropost.com/api/tracking/parcel|shipment?key=…&trackCode=…`:
  часть номеров (`DBRPST…`) ищется как parcel, остальные — как shipment; ключ публичный и вынесен
  в настройку `DOBROPOST_API_KEY`. Если API недоступен с хостинга, используется тот же ответ через
  прокси Google Translate (`DOBROPOST_PROXY_BASE`), затем legacy-страницы `tracking.dobropost.com`.
  Ответ 404 показывается как «Трек-номер не найден в системе Добропоста», ошибки не затирают статус.
  Адаптер живёт в `backend/app/services/tracking.py` — при смене API правится один модуль.

## 4.3 Автостатусы заказа по треку Добропоста

- Логика: до статуса **«Ожидает оплаты доставки»** заказ ведёт основатель вручную
  (оформляется → выкуплен → в пути на склад → на складе → ожидает оплаты).
  После этого менеджер вводит в карточке заказа **трек-номер Добропоста** — и дальше
  фоновая задача (`OrderTrackingWorker`) сама двигает статус заказа по данным их API
  раз в `TRACKING_REFRESH_HOURS` часов (по умолчанию 6).
- Статус меняется только вперёд (таможня → в пути до получателя → доставлен),
  без откатов; отменённые и доставленные заказы не трогаются; ручная зона не затрагивается.
  Клиенту уходит обычное уведомление, в истории событие с `source: dobropost` и текстом статуса перевозчика.
- В карточках заказа (клиентская и админская) видны «Статус Добропоста», «Проверено»,
  «Следующая проверка»; при вводе трека проверка запускается в течение минуты.
- Таблица `orders` пополнилась полями `tracking_status_text`, `tracking_checked_at`,
  `tracking_next_check_at` + индекс, миграция `0006`; включается/выключается `ORDER_TRACKING_ENABLED`.
- Маппинг статусов перевозчика осторожный (доставлен/курьер/таможня/склад/выкуп/оформление);
  если Добропост использует другую формулировку, она сохраняется как «Статус Добропоста»
  и видна менеджеру, а маппинг правится в `backend/app/services/order_tracking.py`.
- Проверено на реальной доставленной посылке (`DBRPST5032227180`): API отдаёт 14 чекпоинтов
  от свежего к старому с полями `statusName` (англ.), `statusRUName`, `statusCategoryId`, `date`.
  Парсер берёт самый свежий чекпоинт и предпочитает русское название; маппинг покрывает
  «На комплектации/взвешивании», «Ожидает оплату», «Ожидает отправку/реестр»,
  «На таможне в Китае», «Поступила на таможню в стране назначения», «Таможенное оформление…»,
  «Подготовлено к отгрузке последней мили», «Передана на доставку по РФ», «Доставлена получателю».

## 5. Деплой на Bothost

Добавлено под реальные требования Bothost (код монтируется в `/app`, данные — в `/app/data`, Dockerfile — в корне репозитория):

- `Dockerfile` в корне — основной образ для Bothost: готовый `frontend/dist` из репозитория (без Node-сборки), Python 3.12 с готовыми wheels, приложение в `/srv/taoji-cargo` (вне `/app`, который Bothost монтирует исходниками), постоянная база в `/app/data`;
- `deploy/Dockerfile.bothost-node` — альтернатива со сборкой фронтенда внутри платформы (если не хотите коммитить `frontend/dist`);
- `deploy/bothost-entrypoint.sh` — `mkdir /app/data` → `DATABASE_URL` по умолчанию → `WEBAPP_URL=https://$DOMAIN` → `alembic upgrade head` → `seed` → запуск;
- `deploy/BOTHOST.md` — пошаговая инструкция: галочка «свой Dockerfile», домен и внутренний порт, тарифы (Starter 256 МБ не подходит, нужен Basic), переменные, `/app/data`, обновления и типовые ошибки;
- `.env.bothost.example` — минимальный набор переменных (BOT_TOKEN/DOMAIN/PORT Bothost подставляет сам).

## 7. Быстрый чек-лист деплоя

1. Сохранить `.env` (секреты) и `data/` (база).
2. Задеплоить контейнер по `deploy/BOTHOST.md`, задать переменные из `.env.bothost.example`.
3. Убедиться, что `/api/health` отвечает `ok`.
4. Нажать `/start` боту с аккаунтов владельца и менеджеров.
5. Обновить Main Mini App URL в BotFather на HTTPS-домен Bothost.
6. Проверить на телефоне: ссылка → расчёт с услугами → оформление → уведомление в чате;
   админка → трек-номер; экран «Мои заказы» → проверка по трек-номеру; бот `/track`.
